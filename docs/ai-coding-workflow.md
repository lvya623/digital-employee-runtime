# 如何管理「大规模 AI 生成代码」

> 对应岗位要求里的最高优先级：能把 AI coding agent 当协作开发者，
> 而不是把生成结果当黑盒合进去。

## 1. 先立契约，再让 AI 批量生成

顺序是 `domain/models.py` → `skills/base.py` → `docs/adr/` → 再生成 `skills/builtin/*`。
契约先固定，AI 生成的代码就只能在预定形状里生长。本仓库 12 个业务 Skill 全部由
同一份 `BaseSkill` 模板生成，彼此结构一致，因此 review 时可以「看一个，懂全部」。

## 2. 用分层把风险关在笼子里

AI 最容易写出「顺手读个数据库」「直接塞一大段 prompt」的代码。
`CLAUDE.md` + `.cursorrules` 把这类行为变成**结构性不可能**：
`skills/` 拿不到 DB session，`domain/` 不能 import 框架，上下文只能由 `context/` 传入。

## 3. 生成 → 验证 → 人审，三步缺一不可

| 步骤 | 机器做 | 人做 |
|---|---|---|
| 生成 | 按 spec 产出模块 + 测试草稿 | 确认 spec 与 ADR 不冲突 |
| 验证 | `pytest -q`、类型检查、ruff | 看测试断言的是行为还是实现 |
| 人审 | diff 统计、来源标记 | 逐行读高风险 Skill、异常分类、幂等处理 |

## 4. 让来源可追溯

AI 生成的模块在 commit message 标注 `Co-authored-by: AI`，
后续做重构时能按来源筛选「需要重点复审」的文件。
标注来源**不代表降低标准**，合入责任始终在人。

## 5. 重构是常态，不是事故

当同类 Skill 出现第三份重复逻辑时，把它上提到 `BaseSkill` 或 `loader.py`，
而不是让 AI 再生成第四份。本仓库做过两次这样的上提：
统一重试策略、统一 `compensation` 注册，记录在 ADR 与提交历史里。

## 6. 可度量的四个指标

1. 生成代码的测试覆盖率（要求与手写代码同标准）
2. 生成模块的返工率（合入后 7 天内被修改的比例）
3. 单次 diff 体积（超过 400 行强制拆分）
4. `except Exception: pass` 出现次数（CI 静态检查，目标为 0）

## 7. 一个诚实的边界

AI 很擅长在**契约明确**的地方批量产出，不擅长替你做架构取舍。
所以本仓库所有 ADR 都由人写，AI 只能在既定决策下实现。
这也是我理解的「协作开发者」：它写得多，但方向由人负责。
